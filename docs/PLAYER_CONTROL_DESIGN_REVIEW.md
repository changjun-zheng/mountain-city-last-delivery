## 1. 总体审查结论

玩家控制系统的方向适合本项目，但目前还不能直接作为完整的开发规格。主要问题是部分文档未同步最新决策、模块之间缺少边界规则，以及连续坡面与候选物理方案存在适配风险。

已确认的核心方向基本一致：

- 移动与跳跃服务于轻松的建筑探索。
- 主动按键交互，并根据交互类型限制玩家控制。
- 实体平台为主，特殊单向平台为辅，第一版不支持主动下落穿透。
- 脚底检测寻找候选支撑面，实际物理接触验证落地。
- 永久进度保留，临时世界状态通过检查点回滚。
- 坠落恢复采用短暂淡出淡入。

需要优先处理三个方面：

| 优先程度 | 问题 | 影响 |
| --- | --- | --- |
| 高 | 玩家控制文档中的移动、跳跃章节仍保留过时状态 | 开发者可能按照旧提案实现 |
| 高 | 恢复、交互、跳跃与检查点更新缺少统一的状态转换规则 | 可能出现自动跳跃、重复恢复或错误快照 |
| 高 | 隐藏连续坡面不能直接依赖 Arcade Physics 的普通碰撞体实现 | 可能影响物理方案和开发成本 |

现有功能数量没有明显超出个人开发范围。真正增加复杂度的是坡面、移动平台、单向碰撞、宽容跳跃和快照恢复同时协作时的边界处理。

## 2. 五个模块分别存在的问题

### 2.1 水平移动系统

存在明确的文档状态冲突。[玩家控制文档](PLAYER_CONTROL_DESIGN.md)中的“移动手感”仍标为 PROPOSED，而[决策记录](DECISIONS.md)已确认平滑加减速、反向先减速及空中方向控制。

还缺少以下细则：

- “空中控制约 80%”具体作用于加速度、减速度还是最大速度。
- 起跳时是否继承当前水平速度。
- 空中反向输入如何减速、转向。
- 交互锁定时，角色已有水平速度如何处理。
- 坡面上的移动速度按水平距离还是沿坡距离计算。

候选参数需要统一测试口径。若按恒定地面加速度计算，从静止达到 3.5H/s 约需 0.292 秒，与旧候选加速时间 0.15～0.25 秒不完全一致。两者都是候选值，不能同时当成固定要求。

### 2.2 跳跃系统

最新正式决策没有完整同步到玩家控制文档。“跳跃规则”仍把可变跳高、土狼时间和输入缓冲列为提案；最新决策已经确认相关机制和基本规则。

需要补齐的状态转换包括：

- 土狼时间起跳后，同一次输入不能再次留在缓冲中触发第二次跳跃。
- 缓冲输入在落地前已经松开时，落地后的跳跃仍应符合短按低跳。
- “松开后的向上速度乘数”何时应用、每次跳跃应用几次，尚未说明。持续每帧相乘会产生明显不同的结果。
- 坡面接缝短暂失去接触时，不能反复恢复跳跃资格。
- 交互、失败、切换场景或窗口失焦时，跳跃缓冲和按键状态如何处理。

候选跳跃高度存在数学不一致。在恒定重力、完整跳跃、忽略碰撞及提前松键的条件下：

- 7.2H/s 初速度与 18H/s² 重力，对应理论高度约 1.44H。
- 同高度起落的理论腾空时间约 0.8 秒。
- 若水平全程保持 3.5H/s，理论距离约 2.8H。

旧文档的候选高度为 2～2.5 个角色高度，两者不能同时满足。水平距离还受角色宽高比例、起跳速度和空中控制影响。这里应统一测试目标，不能据此直接修改最终参数。

### 2.3 交互系统

主动交互、统一入口和按类型限制移动的方向清楚，与任务自动接取机制兼容。

缺失的关键边界是：

- 对话或调查是否允许在空中开始。
- 锁定移动是否停止现有速度，以及是否继续受重力和移动平台影响。
- 对话结束、关闭阅读界面、失败恢复同时发生时，谁负责恢复控制。
- 交互期间按下的移动或跳跃输入，结束后是否立即生效。
- 同一个 E 输入是否会同时触发交互、推进对话和重复操作。
- 隔墙、隔楼层或被遮挡的对象，是否属于有效目标。

“优先朝向，再选择合适的最近目标”适合作为原则，但需要稳定的目标保持规则，避免玩家站在两个对象之间时提示不断切换。

[任务系统文档](QUEST_SYSTEM_DESIGN.md)仍笼统表示拾取交互方式未确定。主动按键与统一入口已经确认，剩余待定内容应缩小到范围、反馈和具体对象行为。

### 2.4 碰撞系统

实体平台、单向平台、禁止主动下落穿透和脚底接触验证在逻辑上兼容。主要问题有四项：

1. **连续坡面与物理候选不直接匹配**。Arcade Physics 的内置碰撞形状只有矩形和圆；连续坡面需要额外处理或其他物理方案，不能假设普通配置即可完成。依据见 [Phaser 官方物理说明](https://docs.phaser.io/phaser/concepts/physics)。
2. **支撑面方向尚未形成可执行判定**。坡面接触不能简单等同于水平平台接触；单向平台从下方穿越、擦到墙角，也不能误判为落地。
3. **移动平台承载规则未确定**。包括随平台移动、起跳时是否继承平台速度、平台复位后如何重新建立接触，以及挤压场景如何处理。
4. **升降平台的确认范围存在歧义**。核心谜题已正式确认“启动升降平台开放路线”，但碰撞提案写着“C3 升降平台如果保留”。应区分平台机制已经确认、C3 具体位置和乘坐表现仍待设计，避免误认为整套平台机制可直接删去。

不支持主动下落穿透本身没有问题，但地图必须提供楼梯、通道或安全边缘出口，避免单向平台成为无法离开的空间。

### 2.5 检查点与失败恢复系统

规则已经比较完整，但恢复后的世界一致性仍是最高风险之一。

尚未闭合的情况包括：

- 初始备用检查点没有正式检查点快照时，第一次失败如何恢复临时世界。
- 永久任务目标已完成，但对应开关、升降平台或通道被回滚后，如何保证任务仍可继续。
- 永久收藏品保留后，场景中的拾取物是否消失，任务奖励如何避免重复发放。
- 恢复到检查点触发区域内，是否会被误判为新进入并立即覆盖快照。
- 连续触发坠落区域时，如何避免启动多次淡出与恢复。
- 回到旧检查点后重新生成快照时，临时状态是否覆盖当前探索范围之外的区域。
- 淡入结束后仍按住跳跃键，是否会发生非预期跳跃。

任务系统文档仍把完成进度如何保留整体列为待讨论，已经落后于“正式完成的任务目标保留”的新决策。任务接取和进行中状态仍可待定，但完成目标的保留原则不应继续悬置。

## 3. 模块之间的潜在冲突

下表是潜在失效场景，尚不代表已经出现实现问题。

| 衔接位置 | 潜在冲突 | 建议补齐的规则 |
| --- | --- | --- |
| 平滑移动 → 交互 | 进入对话后已有惯性仍使角色滑出范围 | 明确进入锁定状态时的速度处理 |
| 跳跃缓冲 → 交互结束 | 对话中积累的跳跃输入在退出后生效 | 明确锁定期间是否接收、保留或丢弃输入 |
| 土狼时间 → 脚底检测 | 接缝抖动反复恢复跳跃资格 | 统一有效落地与资格恢复判定 |
| 单向平台 → 脚底检测 | 从下方穿越时重叠脚底区域，被误判落地 | 支撑判定必须服从有效物理接触方向 |
| 永久任务 → 临时路线 | 任务完成保留，关键路线关闭，形成软锁 | 为每个完成目标定义恢复后的必要世界结果 |
| 恢复传送 → 检查点进入 | 传送落入触发区，错误刷新刚恢复的快照 | 区分恢复放置与正常探索进入 |
| 对话结束 → 失败恢复 | 对话关闭回调提前解除失败锁定 | 统一控制权优先级 |
| 淡入 → B2 镜头演出 | 两套摄像机逻辑同时抢控制 | 明确失败恢复与演出的中断、重入关系 |

建议采用明确的控制状态，例如正常探索、交互、镜头演出、失败恢复；地面、空中和支撑对象作为运动状态管理。这是待确认的组织建议，不是新增正式设计。

## 4. 必须在开发前解决的问题

这里指进入相应模块实现前必须有明确答案，不要求先确定全部数值。

1. **整理当前有效规格**。同步移动、跳跃和任务恢复状态；旧规则保留历史标记，不再与当前规则并列。
2. **确定物理验证路线**。连续坡面、单向平台、脚底接触和移动平台需要在同一套方案中验证。
3. **统一跳跃输入生命周期**。明确按下、松开、缓冲消费、土狼资格消费和锁定期间输入处理。
4. **确定控制权优先级**。失败恢复、对话、阅读、机关和镜头演出不能各自独立解除控制锁。
5. **补齐最小恢复状态表**。列出原型中每项任务、收藏品、开关、平台和路线属于永久还是临时，以及恢复后的结果。
6. **决定备用检查点的初始世界恢复依据**。可以只覆盖原型范围，但必须避免“有恢复位置、没有可恢复世界状态”。
7. **定义恢复期间的触发处理**。包括禁止重复失败、恢复传送是否产生检查点进入事件，以及恢复完成前允许哪些系统更新。

最终键位、全部关卡坐标和跨会话存档方案，可以晚于最小运动验证确定；不能因此让原型默认承担未确认的正式需求。

## 5. 可以留到灰盒测试阶段验证的问题

| 类别 | 可以通过灰盒逐步校准 |
| --- | --- |
| 移动 | 最大速度、加减速度、空中控制比例、反向响应 |
| 跳跃 | 初速度、重力、松键截断力度、土狼与缓冲时长 |
| 空间 | 平台间隙、高差、楼梯坡度、走廊宽度、摄像机显示范围 |
| 碰撞 | 主角和脚底区域尺寸、接触容差、平台边缘及接缝表现 |
| 交互 | 有效范围、目标切换稳定性、提示反馈、拾取反馈时间 |
| 检查点 | 触发区域、防止边界意外刷新、安全恢复位置 |
| 恢复 | 淡出淡入时长、曲线、摄像机重定位的具体时机 |

数值验证之前要先明确含义。例如 H 的测量基准、空中控制 80% 的作用对象、松键乘数的应用次数，都不能靠试玩自行补定义。

## 6. 推荐的灰盒原型开发顺序

以下顺序供后续开发确认使用，不构成本次开发授权。

1. **最小碰撞试验场**。平地、连续坡面、实体平台、单向平台和脚底接触；优先验证物理候选。
2. **水平移动**。加速、松键减速、反向、坡面停止和平台边缘。
3. **完整跳跃**。加入可变跳高、土狼时间和缓冲，验证组合边界。
4. **主动交互与控制锁**。使用占位 NPC、调查点、拾取物和机关，验证输入与控制权。
5. **最小检查点恢复闭环**。备用出生点、一个正式检查点、一个临时开关、一项永久进度及淡出淡入。
6. **重复激活与移动平台**。增加第二个检查点、重新进入刷新、升降平台承载和回滚。
7. **C 区小片段与双平台验证**。用少量灰盒区域串联探索、交互和恢复；尽早验证一次 Windows 打包，避免最后才发现资源或输入问题。

原型无需一次搭建完整 A—D 地图，也无需先制作正式美术。

## 7. 每个模块的验收标准

这些是建议的验收条件，不代表已经测试通过，也不将候选参数转为最终参数。

| 模块 | 建议验收标准 |
| --- | --- |
| 水平移动 | 加减速连续；反向先减速再转向；停止不明显滑行；坡面停止不下滑；不同帧率下速度与距离基本一致 |
| 跳跃 | 短按与长按高度可区分；土狼窗口内可起跳、过期不可；缓冲落地只消费一次；落地前松键仍低跳；长按不无限连跳；无意外额外起跳 |
| 交互 | 范围提示正确出现和消失；一次输入只作用于正确目标；原则上单一提示；对话、调查、阅读期间不能移动或跳跃；退出后恢复正确，不误消费旧输入 |
| 碰撞 | 实体平台不能从下方穿透；单向平台可上穿并落地；不能主动下穿但可离开边缘；重叠触发区不能伪造落地；坡面和接缝不卡顿；移动平台承载与复位符合后续确认规则 |
| 检查点与恢复 | 首个正式检查点前返回出生点；新检查点接管；持续停留不刷新、真实离开再进入会刷新；永久进度不丢失或重复奖励；临时状态正确回滚；淡入完成前控制保持锁定；恢复不引发重复失败或错误快照更新 |

还应安排组合验收：移动中开始对话、缓冲跳跃遇到单向平台、坡面边缘起跳、升降平台上失败、恢复落入检查点区域，以及窗口失焦后返回。

## 8. 技术选型建议

Phaser 3 + TypeScript + Vite + Electron 可以继续作为优先候选，适合复用网页与 Windows 两端的主要游戏逻辑。物理方案需要单独验证，不能因为选了 Phaser 就直接锁定 Arcade Physics。

| 候选部分 | 审查判断 |
| --- | --- |
| Phaser 3 | 与当前 2D、键盘探索及环境解谜方向匹配；主要风险在角色物理与复杂建筑接缝 |
| TypeScript | 适合约束玩家状态、交互类型、永久进度与快照字段，建议保留 |
| Vite | 适合网页开发和静态构建；需要验证网页发布路径与桌面资源路径 |
| Electron | 可以承载 Windows 独立程序；需接受运行时体积、内存和打包维护成本 |

### 8.1 物理方案

官方资料说明，Arcade Physics 只内置矩形、圆形碰撞；Matter 支持更复杂形状，两者的物理对象不能直接互相碰撞。因此，不能简单让角色使用 Arcade、楼梯使用 Matter 来完成接触。依据见 [Phaser 官方物理说明](https://docs.phaser.io/phaser/concepts/physics)。

建议后续优先做一个 Matter 路线的限量技术试验，验证连续坡面、停止不滑动、单向平台和可控跳跃。Matter 支持复杂形状，并不意味着这些手感要求会自动满足。Arcade 加自定义坡面仍可评估，但会增加自定义碰撞与接触验证工作。

不建议个人开发同时维护两套完整角色物理实现，也不建议在没有验证的情况下推翻已确认的坡面设计。本建议不将 Matter 或其他物理实现锁定为正式技术决策。

### 8.2 双平台需要提前验证的风险

- **资源加载与发布方式**。网页通过网址访问，与双击本地 HTML 是不同运行条件。建议先确认前者是否满足网页目标；桌面端验证打包后的资源路径。Vite 支持静态部署和相对资源路径，但需要实际验证。参考 [静态部署说明](https://vite.dev/guide/static-deploy.html)和[资源基础路径说明](https://github.com/vitejs/vite/blob/main/docs/guide/build.md)。
- **输入与窗口状态**。验证 Space/方向键是否导致页面滚动，点击菜单后的焦点、切换窗口后的按键状态、全屏及不同窗口尺寸。
- **运行时一致性**。固定候选版本后比较浏览器与 Electron 的运动、碰撞和恢复表现；开发服务器可运行不能代替发行包验证。
- **桌面发行成本**。Electron 内置 Chromium 和 Node.js，具有额外运行时开销；打包是独立工作，应在早期验证最小产物。参考 [Electron 官方介绍](https://www.electronjs.org/docs/latest/)和[打包说明](https://www.electronjs.org/docs/latest/tutorial/application-distribution)。
- **存档边界**。网页存储与桌面文件存储不能直接当成同一套机制；当前永久进度保留只确定失败恢复语义，跨会话保存仍需后续设计。
- **类型检查**。Vite 转译 TypeScript 不等于执行类型检查，后续工程需要单独安排类型检查。参考 [Vite 官方说明](https://github.com/vitejs/vite/blob/main/docs/guide/features.md)。

## 后续处理建议

建议先由项目负责人确认本报告中的开发前规则，再维护正式策划文档：优先同步玩家控制文档的移动、跳跃章节，并补充控制状态转换和最小恢复状态表。所有候选技术与测试数值继续保持候选状态。

本报告仅整理审查结果，不修改其他策划文档中的正式决策，不启动游戏开发。
