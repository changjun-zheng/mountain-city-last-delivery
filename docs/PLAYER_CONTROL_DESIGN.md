## 玩家控制协调与状态组织

### PC-01：统一玩家控制协调器

状态：CONFIRMED。确认日期：2026-11-07。依据：项目负责人本次明确指示。

1. 玩家控制状态由统一的 Player Control Coordinator 管理。
2. 所有游戏系统只能向协调器请求开始或结束控制状态。
3. 只有协调器有权决定是否开放玩家控制。
4. 移动、跳跃、交互、镜头演出和失败恢复不得分别维护互相独立的全局控制锁。
5. 玩家运动状态与控制状态分离管理。
6. 运动状态包括地面、空中、坡面及移动平台支撑等信息。

本条确认协调职责和状态分离原则；以下具体状态划分、优先级、会话和物理行为仍为提案。

### PROPOSED：控制状态划分

建议包括 Exploration、Dialogue、Reading、Mechanism、Cutscene、Failure、Recovery。地面、空中、坡面和移动平台属于独立运动信息，不混入控制状态划分。

### PROPOSED：状态优先级与切换

建议优先级：Failure / Recovery > Cutscene > Dialogue / Reading / Mechanism > Exploration。

- 失败恢复可以打断其他状态。
- 镜头演出不强行打断正常交互，等待交互结束后重新判断触发条件。
- 对话、阅读和持续机关操作互斥。
- 普通拾取不切换主控制状态。

### PROPOSED：控制权会话管理

建议使用 Session ID。结束状态的请求必须匹配当前会话，防止旧对话或旧动画回调意外解除新的控制锁。会话方案尚未正式确定，不将其当作 PC-01 的必选实现。

### PROPOSED：锁定期间的物理行为

- 对话和阅读期间清除角色水平惯性。
- 保留正常重力、碰撞和支撑关系。
- 需要锁定的交互原则上只能在稳定支撑时开始。
- 失败恢复期间暂停临时世界运动。
- 恢复完成后重新建立有效支撑信息。

上述物理行为均待确认，不因控制限制已确认而自动生效，也不改变既有碰撞、检查点和淡出淡入恢复规则。

## 2. 跳跃系统 Jump System

### 历史提案：跳跃规则

原状态 PROPOSED，保留追溯。可变跳跃高度、土狼时间和跳跃缓冲的现行正式规则见决策记录及 [HONGYADONG_LEVEL_DESIGN.md](HONGYADONG_LEVEL_DESIGN.md)“土狼时间与跳跃输入缓冲”；具体实现与数值仍待验证。以下旧提案不将已确认机制重新降为候选，也不擅自确认其他能力。

- 单次跳跃，不设置二段跳。
- 支持可变跳跃高度；按键时长与高度之间的具体关系待验证。
- 加入土狼时间：离开平台边缘后，短时间内仍允许起跳。
- 加入跳跃缓冲：落地前短时间输入跳跃，可在满足起跳条件时生效。

### PC-02：一次性跳跃输入请求

状态：CONFIRMED。确认日期：2026-11-07。依据：项目负责人本次明确指示。

1. 一次有效的跳跃按下只产生一次跳跃请求。
2. 按键自动重复不产生新的跳跃请求。
3. 正常探索状态下，满足有效落地或土狼时间条件时立即起跳。
4. 不满足立即起跳条件时，允许进入已有设计确定的单次跳跃缓冲。
5. 成功起跳时消费对应请求和跳跃资格。
6. 锁定、失败恢复及窗口失焦时清理跳跃请求与缓冲。
7. 控制恢复后，必须先松开跳跃键，再次按下才允许产生新的请求。
8. 持续按住跳跃键不得在控制恢复后自动起跳。

本条不锁定具体键位、参数或输入实现，也不新增跳跃能力。

### PROPOSED：跳跃输入细化

以下为细化提案，不把未确认的实现方式升级为正式决策。已确认部分仅作为约束重述：

- 建议使用 Pressed、Held、Released 区分输入。
- 一次按下产生一次请求、缓冲只保留一个请求、土狼起跳消费对应资格，沿用正式规则；具体输入组织方式仍待确认。
- 起跳前的旧接触信息不能恢复跳跃资格。
- 缓冲输入提前松开时，落地触发低跳，沿用此前已确认的短按低跳原则；具体处理方案仍待确认。
- 松键截断每次跳跃最多执行一次。
- 锁定期间不接受新跳跃请求。
- 失焦后清理输入，不补发失焦期间的输入；PC-02 已确认的请求与缓冲清理规则继续有效。

### TO_VALIDATE：初始测试参数

| 项目 | 初始测试参数（非最终值） |
| --- | --- |
| 土狼时间 | 100～120 ms |
| 跳跃缓冲 | 100～150 ms |
| 跳跃高度 | 2～2.5 个角色高度 |
| 跳跃距离 | 3～4 个角色宽度 |

角色尺寸的测量基准、跳跃距离的测量条件、重力及起跳速度均待确定。以上范围用于后续试玩校准，不能据此锁定最终关卡间距。

## 3. 交互系统 Interaction System

### CONFIRMED：主动按键与统一交互入口

确认日期：2026-11-07。依据：项目负责人本次明确指示。

1. 玩家进入可交互对象的有效范围后显示交互提示。
2. 玩家必须主动按下交互键才能触发交互，不采用靠近后自动触发对话或调查的方式。
3. 离开交互范围后，提示自动消失。
4. 同一时间原则上只显示一个主要交互提示，避免多个提示冲突。
5. NPC 对话、环境调查、物品拾取和机关操作共用统一交互入口，由交互对象类型决定具体行为。

交互目标选择原则：优先考虑玩家正在面对的有效对象；多个对象同时处于范围内时，优先选择合适的最近目标。具体交互范围、优先级细则及同等条件下的目标选择仍待灰盒验证。

### PROPOSED / TO_VALIDATE：默认键位与提示文案

| 交互类型 | 当前默认提示建议 |
| --- | --- |
| NPC 对话 | E 对话 |
| 环境调查 | E 调查 |
| 物品拾取 | E 拾取 |
| 机关操作 | E 操作 |

E 为当前默认交互键位建议，需结合网页与 Windows 平台输入设计验证；不因统一交互入口已确认而锁定 E 键。左右移动 A/D 或方向键、跳跃 Space 仍为候选键位，完整候选映射见移动系统。

主动交互适用于上述四类对象，不新增自动交互机制；既有检查点进入区域自动激活规则继续有效。NPC 任务仍按主动交互并了解委托后自动接取的既有规则执行。

### CONFIRMED：交互期间的玩家控制

确认日期：2026-11-07。依据：项目负责人本次明确指示。

根据交互类型暂时限制角色移动：

| 交互类型 | 玩家控制规则 |
| --- | --- |
| NPC 对话 | 对话期间锁定角色移动和跳跃 |
| 建筑调查 | 调查期间锁定角色移动和跳跃 |
| 文化知识阅读 | 阅读期间锁定角色移动和跳跃 |
| 机关操作 | 根据具体操作类型决定是否限制移动 |
| 普通物品拾取 | 只播放短暂反馈，不设置长时间移动锁定 |

交互结束后，相应系统向 Player Control Coordinator 请求结束控制状态，是否开放玩家控制由协调器决定（PC-01）；不由交互系统单独解除全局锁。上述控制规则不改变主动按键交互、范围提示、原则上单一主要提示与统一交互入口；E 仍是默认键位候选，任务自动接取和检查点进入区域自动激活规则继续有效。

待详细设计（TO_VALIDATE）：各机关操作的具体控制限制、普通拾取反馈时长及具体表现。不得将普通拾取直接扩大为长时间锁定，也不在本次确定具体时长。

### TO_VALIDATE：交互细节

交互范围、朝向与距离的具体优先级、同等条件下的目标选择，以及提示的具体表现与交互反馈方式均待灰盒验证或详细设计。本次确认选择原则，不锁定算法或数值，也不将既有“推拉”等能力候选改为正式决策。

捕获期交互约束（CONFIRMED，2026-11-08）：检查点快照捕获期间，已登记快照对象的交互请求被屏蔽，不缓冲、不排队；捕获结束后须重新按下交互键，持续按住不自动触发。无关对象的正常交互以及移动和移动输入不受该局部屏蔽影响。完整规则见检查点系统“新检查点捕获期间屏蔽已登记快照对象的交互请求”；此处不锁定 E 键，也不改变对话、阅读等既有控制限制。

## 4. 碰撞系统 Collision System

### CONFIRMED：美术台阶与隐藏连续坡面

确认日期：2026-11-07。依据：项目负责人本次明确指示。

1. 美术上保留真实多级木质楼梯或石阶的外观。
2. 物理碰撞使用隐藏的连续坡面，不要求每一级台阶独立参与碰撞。
3. 玩家可以自然地沿坡面上下移动，在坡面停止时不应自动滑动。
4. 楼梯与上下平台连接处应避免卡顿。
5. 具体坡度、尺寸及碰撞参数仍待灰盒验证。

此前“楼梯优先采用台阶式碰撞结构”为历史提案，现由本条正式决策替代；台阶外观继续保留。该决策不锁定物理框架或实现方式。

### CONFIRMED：普通实体平台与特殊单向平台

确认日期：2026-11-07。依据：项目负责人本次明确指示。

1. 普通实体平台不允许角色从下方穿透，允许角色正常站立和行走。
2. 特殊单向平台允许角色从下方跳跃穿过；从平台上方落下时可以正常站立，并允许正常行走。
3. 只有经过明确设计的特殊平台才使用单向碰撞，不得将所有建筑地面和楼层统一设为单向平台。
4. 第一版不支持通过下方向键加跳跃键等专门输入，主动穿过脚下的单向平台下落。
5. 前往下层需要通过楼梯、正常通道或走到平台边缘后自然下落；禁止主动下落穿透不限制正常离开平台边缘。

第 4、5 项于 2026-11-07 正式确认。主动下落穿透不列为第一版开发需求；只有后续灰盒测试发现该功能确实有助于关卡探索时，才在后续版本重新评估，当前不实现。

关卡应用原则：普通实体平台主要用于建筑楼层、木质走廊、石板路、普通观景平台和 C3 下层建筑通道；特殊单向平台可按地图需要用于 C2 特殊错层平台及隐藏探索路线。具体位置、数量仍待设计，不构成最终地图布局。

待验证：单向碰撞检测实现、从下方穿越的碰撞处理、平台边缘表现、与墙壁/楼梯/其他平台的连接、特殊平台数量与位置及灰盒测试结果。上述规则不改变已确认的楼梯连续坡面方案，不锁定物理框架。

### CONFIRMED：独立脚底检测区域与物理接触验证

确认日期：2026-11-07。依据：项目负责人本次明确指示。

1. 主角具有独立的非阻挡性脚底检测区域，用于寻找可能的有效支撑面。
2. 必须结合实际物理碰撞接触信息确认是否落地，不得仅凭检测区域重叠判定落地。
3. 落地判定应考虑有效支撑面的接触方向。
4. 普通地面、实体平台、特殊单向平台、楼梯坡面及移动平台可以成为有效支撑面；仍须满足上述接触验证条件。
5. NPC、调查对象和普通交互触发区域不属于有效支撑面。
6. 检测区域尺寸、位置和接触判定参数仍待灰盒验证。

移动平台可作为支撑面的规则不确定其具体配置或承载实现，也不改变特殊单向平台的穿越规则。

### CONFIRMED：碰撞设计原则

- 美术轮廓与物理碰撞分离。
- 简化墙壁、地面和装饰物的碰撞结构。
- 尽量保持相邻平台支撑表面连续。
- 避免墙角、碰撞接缝造成角色卡顿。
- 不追求像素级碰撞。

以上为设计原则，具体处理方案仍为提案或待验证内容。

### PROPOSED：碰撞设计

- 原“主角碰撞体与美术轮廓分离”提案现已归入上述正式设计原则，保留此处记录供追溯。
- 历史提案“地面和平台使用统一的实体碰撞规则”中的平台分类，现以上述普通实体平台与特殊单向平台正式决策为准；其余地面碰撞细节仍待设计。
- 墙壁阻止角色穿越，装饰物不默认参与碰撞。
- 天花板阻止角色向上穿透。
- 历史提案“正常平台边缘允许玩家离开并进入下落状态”现由上述平台规则确认为允许正常离开边缘；具体边缘碰撞表现仍待验证。
- 坠落检测使用独立触发区域。
- NPC、调查点、纪念品和检查点使用独立触发检测，不默认设置实体阻挡。

### 工程验证：M1.2.1 固定步与生命周期暂停

本节仅记录按任务实施的最小运行时，不新增或修改 CONFIRMED 设计决策。共享核心已建立固定步累加器、有界补算及 Runtime Lifecycle Controller，Renderer 展示一个诊断移动标记，不是正式玩家。

- 原型配置为 20 ms 固定步（50 Hz）、每帧最多 5 步，标记以 100 单位／秒循环移动；数值均为可调整的工程验证值，不是最终游戏或物理参数。
- 实际执行一步才递增 SimulationTick；过载丢弃完整步时间，保留不足一步的余量，不补发玩法事件。暂停保留此前余量，恢复后的首个帧样本重新建立基线。
- Owner 和 Request Key 由来源生成并持有，Controller 创建独立 Token；工程实现使用实例内 symbol 身份。Owner + Key 去重，准确 Token + Owner 才可释放；旧 Key 保留退役记录，不能重启旧请求。集合非空保持暂停，协议不依赖 Tick 或检查点。
- Web 与 Electron Renderer 均将 document.visibilitychange 转换为同一暂停协议。页面隐藏或 Windows 原生最小化期间暂停，恢复后不追赶后台时间。未新增 Preload 或 IPC；实际测试证据、命令及覆盖边界见 [README.md](../README.md)。

记录限于固定步和诊断场景，玩家控制、碰撞、Matter T01–T06 和首关 MVP-G01–G06 不在此项验收范围。

Single Codebase, Web-first, Shared Game Core（CONFIRMED，2026-11-09）：平台适配层接入输入设备和生命周期信号，两端复用同一玩家控制、碰撞与模拟规则，并在早期原型验证 Windows 兼容性。平台恢复运行不改变 PC-01 的控制权、PC-02 的失焦清理及检查点恢复约束。物理回调仍遵守固定阶段事件分发和 SimulationTick 批次边界；固定时间步及累加器已确认，模拟频率与性能阈值仍为 PROPOSED。

Fixed Timestep Simulation with Accumulator（CONFIRMED，2026-11-09）：玩家控制等核心逻辑与物理以相同的固定模拟步推进，渲染独立。累加器管理模拟推进，每个固定步对应一个 SimulationTick，不能用单个异常大的时间步推进物理。Web 和 Windows 使用相同的模拟时间步配置；沿用现有事件收集、批次关闭、仲裁和恢复约束。

Bounded Catch-up with Excess Time Discard（CONFIRMED，2026-11-09）：每帧补算有上限，达到上限后丢弃剩余完整步时间并保留不足一步的余量。只为实际执行的模拟步推进 SimulationTick；丢弃时间不补发事件或推进事务。页面隐藏或窗口最小化时暂停模拟，恢复时重建有效时间采样基线、不补算后台时间，也不重复执行已处理事件。两端共享此规则，不改变控制权、输入清理、检查点恢复或事件与事务身份。频率、每帧补算上限的数值、暂停恢复的具体实现和恢复时是否清除余量等见 [DECISIONS.md](DECISIONS.md) 的 PROPOSED 清单。

Centralized Runtime Lifecycle Controller（CONFIRMED，2026-11-09）：平台适配层仅接收并转换生命周期信号；共享核心的控制器通过平台无关接口协调 Simulation Runtime 暂停与恢复，无需等待 SimulationTick、普通游戏事件分发或 CheckpointCoordinator。暂停不产生模拟步；恢复时重建有效时间采样基线，不补算后台时间。平台适配层和生命周期控制器不接管 PC-01 的玩家控制权；PC-02 的失焦输入清理规则仍有效。运行时恢复不触发检查点恢复或解除既有恢复锁，不改写永久进度、任务进度或 Event ID、Command ID、Transaction ID。具体状态转换与信号映射等见 [DECISIONS.md](DECISIONS.md) 的 PROPOSED 清单。

Pause Reason Set（CONFIRMED，2026-11-09）：模拟暂停来源统一经 Runtime Lifecycle Controller 请求添加或解除对应原因。集合非空时继续暂停，全部解除后才允许协调恢复；重复添加或解除同一原因不改变结果。Simulation Runtime 不判断原因，平台适配层不直接改集合或控制模拟。原因集合不替代 PC-01 的控制锁或检查点恢复锁，也不改变 PC-02 的失焦输入清理。

Owner-scoped Pause Token（CONFIRMED，2026-11-09）：每个独立有效暂停请求对应一个有唯一 Owner 的 Pause Token，由控制器创建登记。重复的持续请求复用原令牌；Owner 只能凭自己的令牌请求释放，不能按原因类型释放其他请求。只要仍有有效令牌，模拟就继续暂停。令牌管理独立于 SimulationTick、普通事件分发和 CheckpointCoordinator，不进入 Event Inbox 或检查点快照，不复用业务身份或 Runtime Instance ID。释放最后一个令牌只允许协调模拟恢复，不解除玩家控制锁或检查点恢复锁。令牌表示、验证、接口和清理等实现仍为 PROPOSED，详见 [DECISIONS.md](DECISIONS.md)。

Pause Token Acquisition and Release Protocol（CONFIRMED，2026-11-09）：采用 Explicit Acquire / Release Protocol。Owner 向 Runtime Lifecycle Controller 申请并持有登记后返回的令牌，凭准确的自有令牌请求释放。持续请求重复申请复用原令牌，不通过引用计数改变暂停状态；重复或无权释放不改变有效集合，新独立请求不得重新激活已释放令牌。Simulation Runtime 不管理令牌，只按控制器协调暂停或恢复；只有集合为空才允许协调恢复。协议不经 CheckpointCoordinator，也不改变 PC-01 的控制权、PC-02 的失焦输入清理或检查点恢复。接口、返回结构和失败处理等仍为 PROPOSED，详见 [DECISIONS.md](DECISIONS.md)。

Pause Request Identity and Deduplication（CONFIRMED，2026-11-09）：Acquire 按 Owner + Request Key 识别请求。同一组合仍有效时重复申请复用原 Pause Token；不同组合不合并，已释放请求的旧 Key 不重新激活令牌，新独立请求须使用新 Key。Request Key 仅用于识别，Release 仍须凭准确的 Pause Token 验证 Owner。此规则不改变有效令牌集合、玩家控制锁或检查点恢复边界。Key 的表示、生命周期、退役记录及旧 Key 返回结果仍为 PROPOSED，详见 [DECISIONS.md](DECISIONS.md)。

Pause Request Key Generation and Lifecycle（CONFIRMED，2026-11-09）：Owner 在首次 Acquire 前生成并持有不透明的 Request Key，同一请求的重复通知与重试沿用原 Key；请求结束后旧 Key 不得重新激活该请求。控制器按 Owner + Key 识别、登记及去重，不生成 Key；释放仍由 Owner + Pause Token 验证。Simulation Runtime 不处理 Key 或 Token，有效令牌集合非空就继续暂停。具体格式、生成算法、创建销毁时机及退役、失败重试处理仍为 PROPOSED，详见 [DECISIONS.md](DECISIONS.md)。

## 5. 检查点系统 Checkpoint System

### CONFIRMED：自动激活与快照恢复

- 检查点采用快照恢复方式。
- 玩家进入指定检查点触发区域时自动激活。
- 激活后保存当前关卡状态。
- 玩家失败后恢复到最近一次激活的检查点快照。
- 环境挑战失败后同样按上述规则恢复；不设置生命值系统，不限制玩家复活次数。

上述恢复规则由下节 2026-11-07 决策细化：坠落失败时永久进度保留，临时世界状态回滚。无生命值与无限复活继续有效，快照字段及具体失败触发条件仍待验证。

### CONFIRMED：坠落失败保留永久进度、回滚临时世界状态

确认日期：2026-11-07。依据：项目负责人本次明确指示。

- 保留已获得的旅行纪念品、历史知识卡、已正式完成的任务目标及已解锁的永久奖励。
- 尚未完成的临时机关步骤、临时开关状态、临时升降平台位置和临时路线状态恢复到检查点快照。
- 玩家位置恢复到当前检查点的安全恢复位置。
- 恢复后清理角色速度、跳跃计时、输入缓冲和交互状态。

此规则适用于坠落失败，不将永久进度的保留等同于已确定跨游戏会话存档方案。

### CONFIRMED：首关 MVP 的恢复边界

确认日期：2026-11-09。依据：[Hongyadong First-Level MVP Design Freeze](DECISIONS.md)。已接取主线、已完成任务目标、C 区机关完成、升降平台路线解锁、奖励发放记录、已获得的文化收藏品（如后续启用）和主线完成均作为永久进度保留。玩家当前坐标、速度与运动状态、未完成的机关操作、平台瞬时运动位置与阶段、NPC 临时对话表现、临时触发器及其余纳入快照的临时世界状态不属于永久进度。

沿用既有两阶段恢复：先还原临时逻辑，重新应用永久效果，再重建物理与视觉、验证世界一致性，成功后才按现有控制权与淡入规则开放玩家控制。仍通过安全锚点放置玩家，清理瞬时速度与输入，清理临时对话并同步触发器占用，不把这些瞬时状态新增为快照字段，不重放旧触发事件。已完成的 C 区机关无需重解，永久开放路线必须保持可通行，即使平台瞬时运动状态回滚；不得重复发放已发放奖励。

首关灰盒可使用既有初始出生备用检查点。正式检查点位置仍为 PROPOSED，不是本次冻结的阻塞条件。快照固定登记、原子捕获、严格版本校验与失败关闭机制继续有效。

### CONFIRMED：永久记录唯一 ID 与幂等恢复

确认日期：2026-11-07。依据：项目负责人本次明确指示。

- 收藏品、任务目标、奖励分别具有稳定唯一 ID，永久世界效果具有独立唯一 ID，各类型保持业务身份，不得混用。
- 同一收藏品不重复获得、同一目标不重复记录、同一奖励事件不重复发奖；同一永久效果重复应用不得产生错误的反向变化。
- 检查点恢复不得清除上述永久记录，场景对象应根据永久记录重新同步。
- 已完成任务目标永久保留，对应永久世界效果优先于快照；普通临时机关仍恢复快照状态，再重新应用永久效果。

建议分类（PROPOSED）：`collectedItemIds`、`completedObjectiveIds`、`claimedRewardIds`、`permanentEffectIds`。仅为数据分类建议，不锁定具体字段、容器或存储实现；详细业务身份见 [QUEST_SYSTEM_DESIGN.md](QUEST_SYSTEM_DESIGN.md)。

本条确认永久记录与世界恢复的语义，不将其等同于跨游戏会话存档。单个当前有效快照和恢复期间屏蔽检查点、坠落触发事件，均按下文正式决策执行。

### CONFIRMED：初始出生点作为备用检查点

### CONFIRMED：初始备用检查点采用完整快照结构

### CONFIRMED：快照管理原则

- 只捕获明确登记的检查点管理对象，不复制整个游戏世界。
- 静态建筑、背景及装饰物不参与快照。
- 记录逻辑状态，不直接复制物理引擎对象内部数据。
- 永久进度与临时快照独立管理。
- 恢复时先恢复临时世界，再重新应用永久世界效果。

永久收藏记录、已完成任务目标、已领取奖励、永久世界效果不放入临时快照；玩家移动和跳跃输入状态、当前交互会话及摄像机过渡动画也不放入临时快照。上述边界不代表对象登记方式、管理范围或一致性方案已确定。

7. 触发器占用状态与快照事务状态独立管理。
8. 玩家离开区域时，正常记录触发器离开状态。

### CONFIRMED：命令交付结果采用四类分类机制

英文名称：Command Handoff Failure Classification。

状态：CONFIRMED。确认日期：2026-11-08。依据：项目负责人本次明确指示。

1. 命令交付结果分为 Accepted、Retryable、Rejected 和 Unknown 四类。
2. Accepted：目标事务管理模块明确成功接受命令，原事件按照既定规则进入 Completed。
3. Retryable：发生暂时性故障，并且能够确认命令尚未被目标模块接受，允许按照后续重试规则再次尝试。
4. Rejected：命令不合法、不受支持或违反系统规则，不允许自动重试。
5. Unknown：无法确认目标模块是否已经接受命令，必须进入异常处理。
6. Unknown 不得直接按照 Retryable 处理。
7. Unknown 状态下禁止盲目重复交付，以避免重复启动业务事务。
8. Accepted 仅代表命令交付成功，不代表业务事务执行成功。
9. 业务事务成功或失败仍然通过独立协调器事件反馈。
10. 保持 Event-Transaction Lifecycle Separation 和 Independent State Modules 的既有架构。

四类名称表示命令交付结果，不是一套自动确定的事件生命周期枚举。Accepted 按既有规则使原事件进入 Completed，但不能作为业务事务成功或安全退役的依据；Retryable、Rejected 的结果分类不自动锁定原事件对应状态。Unknown 是接受结果不确定的异常分类，不能据此认定未接受、重新交付或直接定为 Completed；核查方向现按 Reconciliation Before Retry 确认为协调器主动查询、确认后分类且不明时保持 Unknown；具体查询实现、异常状态及是否暂停其他相关事务操作仍待设计，不自动等同于检查点 RecoveryError。

事件去重不能证明命令未被目标模块接受，也不能代替命令交付防重。命令身份现按 Stable Command ID 确认，目标模块使用稳定 Command ID 识别且不得重复启动事务；具体生成、去重记录与清理实现仍为提案，保留原 Event ID 的既有规则不因此改变，Event ID 与 Command ID 不得混用。Retryable 只确认满足条件时可按后续规则重试，不确定重试次数、间隔或调度方式；它不改变未胜出或全局捕获锁阻挡请求不缓存、不排队、不自动补发的既有规则。已 Completed 原事件不因业务事务失败重新执行。

### CONFIRMED：Unknown 命令交付结果必须先核查，再允许重试

英文名称：Reconciliation Before Retry。

状态：CONFIRMED。确认日期：2026-11-08。依据：项目负责人本次明确指示。

1. 发生 Unknown 时，保留原事件及其去重记录。
2. 暂停同一命令的再次交付。
3. CheckpointCoordinator 主动向目标事务管理模块查询原命令的处理情况。
4. 确认目标模块已经接受命令，按 Accepted 处理，不得重复交付。
5. 确认目标模块从未接受命令，根据实际原因分类为 Retryable 或 Rejected。
6. 只有确认属于 Retryable，才允许进入后续重试流程。
7. 仍然无法确认时，继续保持 Unknown。
8. 查询失败或结果不明确，不能视为命令未被接受。
9. Unknown 期间禁止盲目重复交付。
10. 保留原事件及其去重信息，直到满足安全清理条件。

本条确认 Unknown 的核查方向，不把 Unknown 直接映射成新的正式事件生命周期状态。核查的是原命令是否已经被目标模块接受，而非业务事务是否成功：确认已接受即按 Accepted 使原事件进入 Completed，不因业务事务失败重新交付。确认从未接受也不能直接认定可重试，仍须按实际原因区分 Retryable 与 Rejected；查询失败或信息不明时继续保持 Unknown，不据此证明未接受。

协调器负责组织查询，不直接读取或修改其他模块内部状态。目标事务管理模块按原 Command ID 提供权威结果，现按 Target Transaction Manager-owned Idempotent Command Acceptance 确认；具体查询接口、响应方式与执行阶段仍待设计。暂停同一命令再次交付已确认，但是否暂停其他相关事务操作未定，不扩展为全局事务暂停、玩家控制锁定或检查点 RecoveryError。查询与异常处理不能绕过既有固定阶段、单轮分发、模块职责及捕获请求不排队规则。

原事件与其 Event ID、去重信息必须保留，不通过重新创建事件或更换 ID 绕过同一命令的重交限制。核查结果明确后也不自动清理记录，仍须满足生产者显式确认、生命周期安全清理条件及连续退役水位线规则；Unknown 查询使用原 Command ID 现已确认；查询结果结构、Command ID 与 Event ID/Transaction ID 的具体关联、命令去重记录与清理实现仍未锁定。

状态：CONFIRMED。确认日期：2026-11-09。依据：项目负责人本次明确指示。

1. Transaction 只保留两种最终结果：Succeeded 和 Failed。
2. Succeeded 表示事务成功完成，最终结果已经确定。
3. Failed 表示事务被判定为最终失败，不能继续执行。
4. 可重试的中间失败不属于最终结果。
5. 恢复中状态不属于最终结果。
6. 仍在执行的事务不属于最终结果。
7. 可重试失败不得立即触发最终结果事件。
8. 只有进入 Succeeded 或 Failed，才允许创建最终 Transaction Result Event。
9. 第一版不增加独立的 Cancelled 第三种终态。
10. 一个 Transaction 仍然最多产生一个最终 Transaction Result Event。

**终态与中间状态**：Succeeded 和 Failed 是已确认的逻辑结果。Failed 的前提按 Failure Only After Retry and Recovery Paths Are Exhausted 确认：没有合法重试且没有安全恢复路径。具体错误判据、可用路径识别及转换时机仍待设计。执行中、恢复中和可重试失败均不产生最终结果事件，已判定为 Failed 的事务不继续执行。第一版不新增 Cancelled 终态；是否支持取消及取消语义仍待设计，不改变已确认的检查点捕获不可因离开而取消的规则。

**职责边界**：Transaction Manager 独立维护事务执行状态，判断事务是否达到终态，不把中间失败视为最终失败。CheckpointCoordinator 接收并处理最终结果事件，不管理内部执行，也不自行推断终态。命令 Accepted、原始 Event Completed 与事务 Succeeded/Failed 分属不同阶段，既有交付、Unknown 核查及事件与事务生命周期分离规则不变。

**最终结果事件**：继续遵守 One Final Result Event per Transaction、Independent Transaction Result Event 和 Complete Identity Association Context。进入 Succeeded 或 Failed 后才允许创建，每笔事务最多一个；携带完整身份关联上下文，重复反馈沿用同一结果 ID。创建失败重新处理创建请求，不重新执行已经完成的业务事务，也不重开原始 Event。非终态重试与恢复继续使用原 Transaction ID；结果事件仍经协调器统一创建、原子提交、自动入队和幂等处理。

### CONFIRMED：只有不存在合法重试或安全恢复路径时，事务才能进入 Failed

英文名称：Failure Only After Retry and Recovery Paths Are Exhausted。

状态：CONFIRMED。确认日期：2026-11-09。依据：项目负责人本次明确指示。

1. Transaction Manager 负责判断事务是否可以进入 Failed。
2. 遇到可恢复错误，保留当前事务，进入重试或恢复流程。
3. 已明确不可重试，且不存在安全恢复路径的错误，可以直接进入 Failed。
4. 达到重试次数上限后，仍须判断是否存在其他合法恢复路径。
5. 恢复失败不自动等于事务最终失败。
6. 只要仍存在合法的重试或安全恢复路径，就不能提前进入 Failed。
7. 事务恢复和重试继续使用原 Transaction ID。
8. 不得通过创建新 Transaction ID 来绕过原事务的失败状态。
9. 只有进入 Succeeded 或 Failed，才允许创建最终 Transaction Result Event。
10. 事务进入终态后，不得因为结果事件创建失败而重新执行已经完成的业务事务。

**Failed 判定**：合法重试与安全恢复两类路径均不存在，才可进入 Failed。重试达到上限或一次恢复失败都不是单独的终态依据，仍须判断是否有其他可用路径。不要求实际尝试所有理论上可能的恢复方式；已确定不可用或不安全的路径，可以直接判定为不存在。安全判据、优先级与选择机制仍待设计。

**职责与事务身份**：Transaction Manager 判定终态并协调合法重试与恢复，保留原事务及 Transaction ID。执行模块报告结果和错误，统一分类与重试判断的职责按 Transaction Manager-owned Failure Classification and Retry Decision 执行。CheckpointCoordinator 接收最终结果事件，不管理内部重试，也不自行决定 Failed。既有命令交付和 Unknown 核查规则保持独立；本条不规定通用事务重试次数，也不修改已确认的检查点恢复与触发器限制。

**结果事件边界**：继续遵守 Two Terminal Transaction Outcomes 和 One Final Result Event per Transaction。仅 Succeeded 或 Failed 才允许创建最终结果事件，每笔事务最多一个，仍携带完整身份关联上下文。终态后若结果事件创建失败，重新处理创建请求，已完成的业务事务不再执行，原始事件仍保持 Completed；未新增业务身份或结果身份分配规则。

### CONFIRMED：检查点恢复采用两阶段恢复机制

10. 淡入完成后恢复玩家控制。

控制状态开始与结束统一经 Player Control Coordinator 管理（PC-01）；恢复时按 PC-02 清理跳跃请求与缓冲，控制恢复后须松开跳跃键再重新按下。七种状态枚举、优先级、Session ID、暂停临时世界运动及恢复后支撑重建仍按上述 PROPOSED 方案处理，不据此改变十步正式流程。

第一版以简单、自然的淡出淡入反馈恢复，不制作复杂消失或重现动画、专门的复杂粒子特效、长时间死亡演出或独立复杂复活动画。
